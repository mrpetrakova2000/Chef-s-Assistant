# Архитектура системы: Chef's Assistant

## 1. Ключевые архитектурные решения

### Решение 1: LangGraph как фреймворк оркестрации агентов
**Обоснование:** LangGraph обеспечивает нативную поддержку циклических рабочих процессов агентов, сохранение состояния и условное ветвление. Фреймворк позволяет четко разделить детерминированную логику (циклы координации) и решения на основе LLM.

### Решение 2: Гибридная архитектура с разделением ответственности
**Обоснование:** LLM обрабатывают задачи, требующие семантического понимания (классификация запросов, генерация рецептов, сопоставление продуктов, сравнение предложений). Детерминированный код управляет координацией, HTTP-запросами к магазинам, парсингом HTML, кэшированием и управлением состоянием.

### Решение 3: Изоляция состояния на уровне сессии
**Обоснование:** Каждая пользовательская сессия поддерживает независимое состояние в памяти сервера без постоянного хранения. Состояние сессии живет только в течение обработки запроса и очищается после ответа.

### Решение 4: Стратегия контролируемой деградации (Graceful Degradation)
**Обоснование:** При сбое внешних сервисов (LLM API, сайты магазинов, таймауты парсинга) система продолжает работу с частичными результатами. Для каждого ингредиента, который не удалось найти, в отчете проставляется отметка "Не найдено".

### Решение 5: Белый список доменов для ссылок
**Обоснование:** Система генерирует ссылки на товары только из предварительно утвержденного списка доменов магазинов, что предотвращает инъекционные атаки.

## 2. Список модулей и их роли

| Модуль | Роль | Ответственность |
|--------|------|------------------|
| **API Gateway** | Входная точка системы | Прием HTTP-запросов, валидация входных данных |
| **Classifier Agent** | Классификация намерения | Анализ текста запроса, определение кулинарной тематики |
| **Planner Agent** | Генерация рецепта | Создание структурированного списка ингредиентов |
| **Coordinator Agent** | Управление циклом обработки | Управление очередью ингредиентов и магазинов |
| **Router Agent** | Маршрутизация по категориям | Определение категории товара в магазине |
| **Parser Agent** | Парсинг товаров | Выполнение HTTP-запросов к сайтам, извлечение товаров |
| **Selector Agent** | Выбор товара в магазине | Выбор наиболее релевантного товара |
| **Comparator Agent** | Сравнение между магазинами | Сравнение предложений, выбор оптимального |
| **Reporter Agent** | Формирование ответа | Создание Markdown-отчета с ценами и ссылками |
| **Cache Agent** | Кэширование | Хранение результатов парсинга и LLM-ответов |

## 3. Основной workflow выполнения задачи

### 3.1 Счастливый путь (Happy Path)

**Этап 1: Прием и классификация запроса**
1. API Gateway принимает запрос, валидирует длину (≤200 символов)
2. Classifier Agent анализирует запрос с помощью LLM
3. При положительной классификации система переходит к следующему этапу

**Этап 2: Генерация рецепта**
1. Planner Agent генерирует структурированный список ингредиентов через LLM
2. Валидация: не более 20 ингредиентов

**Этап 3: Координация обработки ингредиентов**
1. Coordinator Agent инициирует цикл по ингредиентам и магазинам
2. Для каждого ингредиента обрабатываются все магазины
3. После обработки всех магазинов выполняется сравнение предложений

**Этап 4: Обработка ингредиента в магазине**
1. Router Agent определяет категорию товара
2. Parser Agent выполняет парсинг категории (до 5 страниц)
3. Selector Agent выбирает наиболее релевантный товар

**Этап 5: Сравнение предложений**
1. Comparator Agent сравнивает предложения из разных магазинов
2. Выбирается оптимальное предложение (цена + релевантность)

**Этап 6: Формирование отчета**
1. Reporter Agent формирует Markdown-отчет
2. Ответ возвращается пользователю в формате JSON

### 3.2 Обработка ошибок

| Сценарий | Действие системы | Поведение для пользователя |
|----------|------------------|---------------------------|
| LLM API недоступен | Retry 2 раза с задержкой | Fallback-ответ |
| Магазин не отвечает | Пропуск магазина | Предложения только из доступных магазинов |
| Ингредиент не найден | Пометка как отсутствующего | Отметка "❌ не найдено" |
| Неверная категория | Fallback-маппинг | Первая доступная категория |
| Глобальный таймаут (300 сек) | Возврат частичных результатов | Отчет с найденными ингредиентами |

## 4. State / Memory / Context Handling

### 4.1 Структура состояния сессии

Состояние сессии хранится в памяти и включает:

**Пользовательский ввод:**
- Исходный текст запроса
- Название блюда
- Количество порций

**Данные рецепта:**
- Список ингредиентов
- Индекс текущего ингредиента
- Индекс текущего магазина

**Результаты поиска:**
- Для каждого ингредиента — список предложений
- Выбранное оптимальное предложение

### 4.2 Политика памяти и очистки данных

| Тип данных | Место хранения | Срок жизни | Условия очистки |
|------------|----------------|------------|-----------------|
| Состояние сессии | Оперативная память | До завершения запроса | После отправки ответа |
| Кэш парсинга | Оперативная память | 6 часов | TTL или ручная очистка |
| Кэш LLM-ответов | Оперативная память | 6 часов | TTL или ручная очистка |
| Пользовательские данные | Не хранятся | - | - |

## 5. Retrieval-контур (поиск товаров)

### 5.1 Источники данных

**Рецепты:**
- Источник: LLM (Mistral)
- Fallback: базовый список ингредиентов

**Товары в магазинах:**
- Источник: Прямой HTTP-парсинг
- Магазины: dixy.ru (полный), magnit.ru (заглушка), vkusvill.ru (заглушка)
- Метод: Selenium (undetected-chromedriver) + BeautifulSoup

### 5.2 Процесс поиска товара

**Шаг 1: Определение категории (Router Agent)**
- LLM сопоставляет ингредиент с категорией
- Fallback: маппинг по ключевым словам

**Шаг 2: Парсинг категории (Parser Agent)**
- Загрузка HTML через Selenium с антидетектом
- Извлечение товаров: название, цена, ссылка
- Пагинация до 5 страниц

**Шаг 3: Выбор товара (Selector Agent)**
- LLM выбирает наиболее релевантный товар
- Fallback: первый товар из списка

### 5.3 Кэширование результатов

| Тип кэша | Ключ | TTL |
|----------|------|-----|
| Категории магазина | `{store}` | 6 часов |
| Товары категории | `{store}:{category_url}` | 6 часов |
| LLM-ответы | MD5 промпта | 6 часов |

## 6. Tool/API-интеграции

### 6.1 Внешние сервисы

| Сервис | Тип интеграции | Назначение | Ограничения |
|--------|----------------|------------|-------------|
| LLM API (Mistral) | REST API | Классификация, генерация, маппинг, выбор | Таймаут 30 сек |
| Сайты магазинов | HTTP/HTML (Selenium) | Получение товаров и цен | Таймаут 30 сек на страницу |

### 6.2 Защитные механизмы

**Валидация входных данных:**
- Максимальная длина запроса: 200 символов

**Белый список доменов:**
- dixy.ru, magnit.ru, vkusvill.ru

**Таймауты:**
- LLM запрос: 30 секунд
- Парсинг страницы: 30 секунд
- Общий таймаут: 300 секунд

**Retry-политика:**
- LLM: 2 попытки с экспоненциальной задержкой
- Парсинг: fallback на пустой список

**Антидетект при парсинге:**
- undetected-chromedriver
- Случайный User-Agent
- Скрытие navigator.webdriver

## 7. Основные failure modes, fallback и guardrails

### 7.1 Сценарии отказов и защита

| Сценарий отказа | Защита | Остаточный риск |
|-----------------|--------|-----------------|
| LLM галлюцинирует ингредиенты | Валидация JSON, промпт с правилами | Редкие блюда могут содержать неточности |
| Неверный маппинг категории | Fallback-маппинг по ключевым словам | ~10% ингредиентов маппятся неоптимально |
| Отказ магазина | Пропуск магазина | Неполные результаты |
| Бесконечный цикл | Ограничение страниц (5), глобальный таймаут | Сложный запрос может быть прерван |
| Утечка памяти | gc.collect() после запроса | При интенсивной нагрузке возможны утечки |

### 7.2 Guardrails (защитные барьеры)

**Валидация ввода:**
- Проверка длины запроса (≤200 символов)

**Очистка состояния:**
- Полная очистка состояния перед каждым запросом
- gc.collect() после обработки

## 8. Технические и операционные ограничения

### 8.1 Latency (время отклика)

| Компонент | Ожидаемое время |
|-----------|-----------------|
| Классификация запроса | 3-5 секунд |
| Генерация рецепта | 10-15 секунд |
| Парсинг категории | 30-60 секунд |
| Выбор товара | 5-10 секунд |
| **Общее время** | **2-5 минут** |

### 8.2 Cost (стоимость)

| Компонент | Ограничение |
|-----------|-------------|
| LLM запросы | Бесплатная квота Mistral API |
| Парсинг магазинов | Без дополнительных затрат |

### 8.3 Операционные ограничения

| Ограничение | Значение |
|-------------|----------|
| Хранение данных | Только оперативная память |
| Максимальное количество ингредиентов | 20 |
| Максимальная длина запроса | 200 символов |
| Максимальное количество страниц парсинга | 5 |

### 9.1 Метрики для мониторинга

| Метрика | Доступ |
|---------|--------|
| Статус системы | `GET /status` |
| Кэшировано категорий | `GET /status` |
| Всего товаров в кэше | `GET /status` |
| Кэшировано LLM-ответов | `GET /status` |
| Количество поисков | `GET /status` |
| Успешность поиска | `GET /status` |
| Время выполнения запроса | `POST /query` |

### 9.2 Логирование

**Что логируем (в консоль):**
- timestamp запроса
- вызовы агентов и результаты
- время выполнения
- ошибки и исключения

**Что НЕ логируем:**
- персональные данные
- полные тексты запросов в персистентном хранилище
